# 基础框架与技术方案的映射

## 执行链路

客户端上传 → 实际解码验证 → SQLite事务写入图片/批次/任务 → Worker领取任务并原子预留预算 → 后端适配器 → 校验结构化结果 → 条件更新任务并写缓存。

首版使用同一数据库作为队列和任务状态存储，因此不存在“数据库提交成功但消息未入队”的双写问题，不需要为单数据库队列再引入Outbox。未来引入外部Broker时，增加事务Outbox和幂等消费者，保留任务表作为事实来源。

图片按SHA-256去重保存在images表，接入只支持文件上传，不实现远程URL下载。图片字节和任务同事务持久化，避免任务已接受但图片引用不可恢复。

## 状态与幂等

- queued：已接受，等待预算或重试时间。
- running：持有随机租约令牌，后台定期续约。
- succeeded：图片调用完成且结构化结果校验通过。
- failed：认证、输入、输出格式或未知执行等不可继续状态。
- cancelled：用户主动取消。
- expired：总截止时间已到。

每次尝试有独立记录。完成操作必须同时匹配task ID、running状态、租约令牌且租约有效；过期工作者不能写入结果或缓存。取消后上游可能已执行，记录unknown尝试，不承诺外部服务恰好执行一次。

批次幂等键约束整次提交；相同键不同请求返回409。图片级去重按版本签名区分：相同图片的独立任务各自保有截止时间与取消语义，在途只允许一个执行，完成后其他任务复用缓存。前一个任务失败后，其他独立任务仍可按各自预算执行，这不等于对失败任务自动重试。

## 调度与故障

领取任务使用BEGIN IMMEDIATE事务，将并发校验、窗口计数、平滑时间检查、租约写入、attempt写入合并为一个原子操作。重启和同主机多进程不会重置预算。缓存命中先于上游预算判断，不消耗尝试次数。

所有同一后端资源共享一个预算域，模型和配额策略一致性在启动时校验。当后端提供更细的配额层级（项目、模型、区域）时，应扩展资源表与原子预留逻辑，使子限额之和仍受上级预算约束。

认证或权限失败暂停后端。429按Retry-After设置共享blocked_until，缺失时采用短暂保守等待。连接建立失败允许有界重试；响应超时、写入/读取链路失败及5xx按“执行结果未知”保守终止，避免对非幂等推理盲目重发。该策略牺牲部分可用性，后续可在上游具备状态查询/幂等保证后放宽。

当前并发约束的是本地有效执行租约。取消、超时或网络分区后，远端推理可能继续，无法用本地取消保证远端已停止。总尝试计数仍保留，不退还已预留预算。

## 单机取舍

SQLite适合启动、验证和小规模单机处理；所有事务尽量短，实际网络调用在事务外执行。GET状态会触发超期维护，因此可能短暂取得写锁。数据库不可用时工作进程不继续领取任务；租约维护失败时停止本地调用并保守处理结果。

生产扩展依次处理：

1. 明确吞吐、峰值和完成时限，测量SQLite锁竞争、图片BLOB增长及队列等待。
2. 对象存储承载输入，保证引用持久化、生命周期和孤立对象回收。
3. 迁移共享数据库与事务Outbox，再引入外部消息队列。
4. 全局预算预留、任务租约、条件提交与凭证状态继续统一协调。
5. 独立后端通过能力/性能验收后接入；不同客户端访问同一上游不算独立容灾。
6. 接入直方图指标、告警、通用熔断、恢复演练及长时间负载验证。

不将当前基础版描述为已具备跨机器高可用或达到99%有效完成率。
